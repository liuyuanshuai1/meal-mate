# 简单管理系统需求文档

## 1. 背景与目标

当前“一起吃饭叭”后端已经具备菜品分类、菜品、Banner、一起吃过记录等基础 API。为了方便维护测试数据和日常内容，需要增加一个简单管理系统。

第一版管理系统采用 FastAPI 内嵌后台页面方案，不做前后端分离，不引入 Vue 或 Node，优先满足“能管理数据、能快速使用”的目标。

推荐方案：

```text
FastAPI
Jinja2
Bootstrap / 简单 CSS
```

管理系统主要服务于本地开发、测试环境或受信任的内部环境，用于快速维护小程序展示数据。

## 2. 功能范围

第一版管理系统包含以下模块：

```text
后台首页
菜品分类管理
菜品管理
Banner 管理
一起吃过记录管理
```

后台页面规划：

```text
/admin
/admin/categories
/admin/foods
/admin/banners
/admin/eat-records
```

## 3. 不做范围

第一版不做以下能力：

```text
后台登录
账号体系
角色权限
操作审计
复杂搜索筛选
批量导入导出
富文本编辑器
独立前端项目
Vue / React 管理后台
Node 构建链路
```

“今晚吃啥查看”不纳入本次管理系统范围。

原因：当前产品设计中，未确认的今晚菜单保存在小程序前端本地 `shopCarInfo`，后端没有当前今晚菜单表或接口。后台无法直接查看、清空或删除用户本地未确认菜单。

后续如果需要后台管理当前今晚菜单，应先新增后端持久化能力，例如 `dinner_plan` 和 `dinner_plan_item`，再增加对应后台页面。

## 4. 页面规划

### 4.1 后台首页 `/admin`

页面目标：作为管理入口，展示各模块导航。

页面内容：

```text
菜品分类管理入口
菜品管理入口
Banner 管理入口
一起吃过记录管理入口
```

交互要求：

```text
点击入口跳转对应管理页面
页面顶部展示简单后台标题
各后台页面保留返回首页或顶部导航
```

### 4.2 菜品分类管理 `/admin/categories`

页面目标：维护小程序菜单页使用的菜品分类。

功能要求：

```text
查看分类列表
新增分类
修改分类
删除分类
```

列表展示字段：

```text
ID
分类名称
排序值
是否启用
创建时间
更新时间
操作
```

表单字段：

```text
分类名称，必填，最长 64 字符
排序值，整数，默认 0
是否启用，布尔值，默认启用
```

删除规则：

```text
删除分类沿用现有软删除逻辑，将 is_active 设置为 false。
如果分类下存在菜品，不物理删除分类。
```

### 4.3 菜品管理 `/admin/foods`

页面目标：维护首页推荐、菜单列表、菜品详情中展示的菜品数据。

功能要求：

```text
查看菜品列表
新增菜品
修改菜品
删除菜品
上传图片
填写图片 URL
设置是否推荐
设置是否上架
```

列表展示字段：

```text
ID
菜品图片
菜品名称
所属分类
参考价格
是否推荐
是否上架
排序值
创建时间
更新时间
操作
```

表单字段：

```text
所属分类，可为空
菜品名称，必填，最长 128 字符
菜品描述，可为空
图片 URL，可为空
图片文件，可选上传
参考价格，数字，必须大于等于 0，默认 0
是否推荐，布尔值，默认否
是否上架，布尔值，默认是
排序值，整数，默认 0
```

图片规则：

```text
管理员可以直接填写图片 URL。
管理员也可以上传图片，上传成功后自动填入图片 URL。
图片上传复用现有 /api/foods/image 能力，或抽出同一套上传处理逻辑供后台使用。
第一版允许 jpg、png、webp，大小限制沿用现有后端规则。
```

删除规则：

```text
删除菜品沿用现有软删除逻辑，将 is_active 设置为 false。
历史一起吃过记录继续保留菜品名称、图片和价格快照。
```

### 4.4 Banner 管理 `/admin/banners`

页面目标：维护首页轮播图。

功能要求：

```text
查看 banner 列表
新增 banner
修改 banner
删除 banner
```

列表展示字段：

```text
ID
图片
标题
跳转类型
跳转目标
排序值
是否启用
创建时间
更新时间
操作
```

表单字段：

```text
标题，可为空，最长 128 字符
图片 URL，必填
跳转类型，取值 none、food、url，默认 none
跳转目标，可为空，最长 256 字符
排序值，整数，默认 0
是否启用，布尔值，默认启用
```

跳转规则：

```text
link_type = none 时，不跳转，link_target 可为空。
link_type = food 时，link_target 填写菜品 ID。
link_type = url 时，link_target 填写 URL。
```

删除规则：

```text
删除 banner 沿用现有软删除逻辑，将 is_active 设置为 false。
```

### 4.5 一起吃过记录管理 `/admin/eat-records`

页面目标：查看和维护用户已经确认生成的“一起吃过”历史记录。

功能要求：

```text
查看历史记录
查看某次详情
删除错误记录
```

列表展示字段：

```text
记录 ID
用户 ID
人物标识
总价
吃饭时间
菜品数量
创建时间
操作
```

详情展示字段：

```text
记录 ID
用户 ID
人物标识
总价
吃饭时间
创建时间
更新时间
菜品明细列表
```

菜品明细展示字段：

```text
菜品 ID
菜品名称
菜品图片
数量
单价
小计
```

删除规则：

```text
删除错误记录沿用现有记录删除逻辑。
删除 eat_record 时，eat_record_item 明细级联删除。
```

第一版默认管理固定测试用户或通过页面参数输入 `user_id` 查询记录。现有后端第一版使用固定 `user_id = 1` 的测试方式，后台可优先按该方式实现。

## 5. 操作流程

### 5.1 新增数据

```text
进入对应管理页面
点击新增
填写表单
提交
保存成功后返回列表
列表展示最新数据
```

### 5.2 修改数据

```text
进入对应管理页面
点击某条记录的编辑
进入编辑表单或展开编辑区域
修改字段
提交
保存成功后返回列表
```

### 5.3 删除数据

```text
进入对应管理页面
点击删除
弹出确认提示
确认后执行删除
删除成功后刷新列表
```

分类、菜品、Banner 的删除优先使用软删除。一起吃过记录删除错误数据时，可以沿用现有物理删除主表并级联删除明细的策略。

## 6. 技术方案

### 6.1 后端结构

建议新增后台路由：

```text
backend/app/routers/admin.py
```

建议新增模板目录：

```text
backend/app/templates/admin/
```

建议模板文件：

```text
base.html
index.html
categories.html
foods.html
banners.html
eat_records.html
eat_record_detail.html
```

后台路由挂载：

```text
/admin
```

### 6.2 页面渲染

```text
使用 Jinja2Templates 渲染 HTML
使用 Bootstrap CDN 或本地简单 CSS
列表页和表单页可以放在同一页面，降低实现复杂度
```

第一版页面不追求复杂交互和视觉效果，只要求信息清晰、操作可用。

### 6.3 数据复用

后台页面直接复用现有模型：

```text
FoodCategory
Food
Banner
EatRecord
EatRecordItem
```

后台行为优先复用现有 API 规则：

```text
分类按 sort asc, id asc 排序
菜品按 sort asc, id asc 排序
Banner 按 sort asc, id asc 排序
一起吃过记录按 eaten_at desc, id desc 排序
```

### 6.4 错误处理

```text
表单校验失败时，在当前页面展示错误提示
保存成功后，在列表页展示成功提示
删除前需要二次确认
数据库错误不直接暴露完整堆栈给页面
```

### 6.5 安全说明

第一版不做后台登录，因此只能部署在本地开发环境、内网环境或其他受信任环境。

如果需要公网访问，必须在后续版本增加至少一种访问控制：

```text
固定密码登录
Basic Auth
反向代理鉴权
账号和角色权限
```

## 9. 方案取舍

方案 A：FastAPI 内嵌后台页面。

优点：

```text
开发快
不需要 Vue
不需要 Node
不需要前后端分离
适合当前测试数据管理
和现有后端集成成本低
```

缺点：

```text
页面视觉效果不会特别精致
复杂交互能力弱
后续如果后台功能变复杂，可能需要迁移到独立前端管理系统
```

结论：第一版推荐采用方案 A。
